# TripFlow 运行、部署与版本管理

适用版本：1.0.1 · 更新日期：2026-10-11

## 1. 唯一工作目录

本电脑使用 `D:\trip flow` 保存项目源码、依赖、文档和构建产物。以后打开编辑器、GitHub Desktop 或终端，都使用这个目录，不再使用原 C 盘开发副本。

目录中的重要入口：

| 文件 / 目录                  | 用途                        |
| ---------------------------- | --------------------------- |
| 启动TripFlow.cmd             | 双击启动本地网站            |
| README.md                    | 项目运行与服务配置          |
| docs/用户使用说明书.md       | 用户操作手册                |
| docs/AI项目架构与改进指南.md | AI / 开发者接手             |
| CHANGELOG.md                 | 每个版本做了哪些改进        |
| AGENTS.md                    | 后续 AI 开发与记录约定      |
| .git/                        | 本地版本历史，不要删除      |
| delivery/                    | 本机交付存档，不提交 GitHub |

旅行和照片的实际数据保存在浏览器或已配置的 Supabase，**不在源码文件夹里**。迁移源码目录不会自动迁移或清除浏览器数据。继续使用 `http://127.0.0.1:5173/tripflow/`，可读取这个来源原有的本地记录；不要为了迁移清理站点数据。

## 2. 本地运行

日常使用：双击项目中的 `启动TripFlow.cmd`。启动后保留命令窗口，关闭时按 Ctrl+C。脚本使用 5173 端口并打开浏览器；如果端口已占用，会报错而不悄悄换地址，以免看到另一套空白浏览器存储。

也可以在 PowerShell 中执行：

```powershell
Set-Location -LiteralPath 'D:\trip flow'
npm.cmd run dev -- --port 5173 --strictPort
```

打开 `http://127.0.0.1:5173/tripflow/`。依赖已随迁移复制，平时不需要重新安装。新电脑或删除依赖后，先运行 `npm.cmd ci`。

所有命令都应在 D 盘项目目录执行。Node、Git、GitHub Desktop 等已安装软件仍可位于系统盘，这不影响项目运行、依赖和输出放在 D 盘。

## 3. GitHub 仓库与个人网站

目标代码仓库：`https://github.com/TheoryOfTheWest/tripflow`。

目标网站：`https://theoryofthewest.github.io/tripflow/`。个人首页仍为 `https://theoryofthewest.github.io/`。

仓库与网站是否已发布，应分别检查 GitHub 远端和 Actions；代码上传成功不代表 Pages 已部署。源码用独立 tripflow 仓库，个人首页可以添加 `/tripflow/` 导航链接。

Pages 初次设置：仓库 Settings → Pages → Source 选择 GitHub Actions，然后在 Actions 运行 `Test and deploy TripFlow to GitHub Pages`。项目已有工作流，不要再添加重复模板。正式地址以 Pages 的 Visit site 为准。

独立仓库发布的备选方案：首次上传时若 Pages 尚未启用，部署工作流可能失败；启用后重新运行即可。以后 main 分支推送会自动触发测试、构建与部署。

## 4. GitHub Desktop 的日常操作

1. 在 GitHub Desktop 中选择 D 盘的 tripflow 仓库；若未列出，使用 File → Add local repository，路径选择 `D:\trip flow`。
2. 开始改进前点击 Fetch origin；若显示 Pull origin，先同步远端修改并检查本地未提交内容。
3. 完成改进后在 Changes 查看文件差异，确认没有私人数据和无关文件。
4. 更新 CHANGELOG，完成适当检查。
5. 在 Summary 写一行改进摘要，在 Description 写原因、变更和验证，点击 Commit to main（如当前使用功能分支，按钮会显示对应分支）。
6. 点击 Push origin 上传；若界面首次显示 Publish repository，则尚未建立远端。
7. 在 History 查看本地每次改进；在 GitHub Commits 查看远端历史；在 Actions 查看网站是否成功更新。

建议提交说明：

```text
fix: 修复跨午夜交通在次日重复计时

问题：午夜结束的路段出现在下一天。
改进：统一使用半开日期区间，保留整段原记录。
验证：对应时间用例、生产构建和相关浏览器流程通过。
```

示例仅展示写法，并不表示当前版本存在或刚修复这个问题。验证内容必须按实际执行结果填写。

## 5. 每次改进的标准流程

用户约定（2026-10-12）：后续修改默认不进行正式网站的在线功能验收；只有用户明确要求线上验证时才执行。按改动影响保留必要的本地检查、本地 E2E、构建和资源路径检查，继续正常提交、推送与发布。部署状态可作简短确认，但不再默认打开正式网站运行交互、真实 API、下载/恢复等在线测试，也不为这一步长时间等待或重试。报告区分“本地验证通过”“已推送/部署”与“未做线上功能验收”。

```text
同步当前代码 → 确认需求 → 改进代码 → 更新文档 / CHANGELOG
  → 运行相关检查 → 提交版本 → 推送 GitHub → 检查 Actions
```

Git 提交记录保存每次具体修改，CHANGELOG 汇总发布版本，package.json 记录当前项目版本。功能变化通常提升次版本，兼容修复或管理改进提升补丁版本；破坏兼容的变更需明确升级与迁移方案。

命令行查看状态：

```powershell
Set-Location -LiteralPath 'D:\trip flow'
git status
git log --oneline -10
git remote -v
```

建议先查看差异再提交，不使用自动“把所有文件直接上传”的定时任务。AI 继续开发时应遵守 AGENTS.md，完成记录与验证；GitHub Desktop 也能看到 AI 用 Git 创建的提交。

## 6. 本次迁移和后续数据

项目已完整复制到 D 盘并逐文件核对。原 C 盘副本保留为回退备份，后续不再用于开发或运行；如确需删除，应在用户明确授权后处理。源码版本管理不包含私人旅行数据库；请在网站中定期导出完整 ZIP，另行妥善保存。

本地与正式网站属于不同来源，记录不会自动共享。需要从本地迁移到正式网站：本地导出完整 ZIP → 打开正式网站 → 选择目标本地模式或云端账户 → 导入为新旅行。

尚未配置 Supabase / Geoapify 时，线上仍是浏览器本地模式 / 坐标网格。配置方法见 README；Publishable Key 和地图浏览器 Key 在仓库 Actions Variables 中设置，禁止使用数据库密码或 Service Role / Secret Key。

## 7. 让 AI 接着改进

提供当前 D 盘完整源码和架构指南，并使用这样的任务描述：

```text
在 D:\trip flow 继续改进 TripFlow，先阅读 AGENTS.md、README、两份主要指南、
CHANGELOG 和相关测试。请完成：[具体需求]。
保留用户现有修改，更新变更记录与受影响文档，执行适当验证。
在本次已授权的 GitHub 同步范围内提交并推送，报告提交和部署的实际状态。
```

长期功能建议在 AI 架构指南的“候选改进路线”中维护；已经完成的内容移入 CHANGELOG，避免把建议重复当成未完成工作。
